Chapter 01 · The problem

First, imagine a coat-check desk.

Each coat is a piece of data. Each rack is a server. We need one repeatable rule that tells us where every coat belongs.

#
A hash function is a label maker.

Give it a key like "photo.jpg" and it always prints the same large number. We use that number to pick a server.

The obvious rule is hash(key) % number_of_servers. It is fast, but the divisor changes whenever a server arrives or leaves.

Chapter 02 · The core idea

Bend the number line into a ring.

A hash can land anywhere from 0 up to a huge maximum. Join the two ends and the range becomes a circle—like a clock.

  1. 1 Hash every server name onto the ring.
  2. 2 Hash every data key onto the same ring.
  3. 3 From a key, walk clockwise to the first server.
The promise

When servers change, most keys keep the same destination. Only a small neighboring slice of the ring is remapped.

Chapter 03 · Routing a key

Clockwise finds the owner.

A key does not choose the nearest server. It chooses the first server clockwise. At the end, the search wraps back to zero.

key: "owl" clockwise → server B

This creates ownership arcs. A server owns all keys after the previous server and up to its own position.

Chapter 04 · Minimal movement

Now change the cluster.

This is the “consistent” part: adding or removing a server changes only the keys in one nearby arc—not almost every key.

Chapter 05 · Virtual nodes

One server, many seats.

A few randomly placed servers can leave one server owning a giant arc. Virtual nodes—or vnodes—give each physical server several positions around the ring.

✦
Think raffle tickets.

One ticket each can produce a lopsided result. Many tickets spread around the bowl make each person's share more even.

  • Better balance across servers
  • Easier capacity weighting
  • Smoother server additions and removals

Chapter 06 · Production thinking

Ownership is not a backup.

A ring tells us the primary owner. For resilience, store copies on the next servers clockwise too. A replication factor of 3 means three distinct physical servers hold each key.

✓Great for

Distributed caches, databases, object stores, sharding.

!Watch out for

Hot keys, node health, replication, and changing membership.

Remember

Consistent hashing minimizes remapping. It does not automatically make data balanced, replicated, or strongly consistent.
